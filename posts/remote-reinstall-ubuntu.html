沒有 IPMI、沒有序列埠：遠端重灌一台 Ubuntu 伺服器

D
Dickens
📅 2026-11-18 📖 14 分鐘閱讀 👁 1 次瀏覽

情境：一台放在機房、人不到現場的 Ubuntu 機器要「換成乾淨系統」。你能做的只有 SSH，其他什麼都沒有——沒有 IPMI、沒有序列埠、沒有 KVM over IP、沒有現場的手。

這種條件下最怕的不是「重灌失敗」，而是「重灌到一半，機器再也連不上」。沒有 console 的機器，一旦開不起來，你連它在哪一行掛掉都不知道，只能跑一趟現場。

💡 這篇是實戰筆記：如何在「只有 SSH」的前提下，用 kexec 進 RAM 救援 → 離線縮小 LVM → debootstrap 裝進新 LV → 一次性開機項試開的流程重灌，並且在每一步都留下「失敗也能自己回來」的活路。文中 IP 與帳號已改寫。

先看限制：為什麼這件事難

一般的遠端重灌教學都預設你有某種「第二條路」可以看畫面。這台機器完全沒有：

缺少的東西造成的後果
IPMI / AMT / BMC 沒有帶外管理，機器斷網就等於失聯，無法遠端開關機、無法看 BIOS
序列埠 console console=ttyS0 沒有設定，開機訊息只出現在實體螢幕上；掛在哪一行只能猜
SSH 金鑰 整台機器沒有任何 authorized_keys，只能用密碼登入——救援環境也得支援密碼
LVM 剩餘空間 VFree = 0，root LV 吃掉整顆 PV，想開新分割區必須先縮小正在用的檔案系統
⚠️ 這四項湊在一起，會讓「重灌」從一個下午的工作，變成一個每一步都要先想好怎麼回頭的工程。
🧭

三條路線，只有一條能留活路

路線做法為什麼不選 / 選
A 原地清空：chroot 進現有 / 重裝一層 ❌ 等於拆自己腳下的地板，裝到一半失敗就兩邊都沒有
B kexec 進 RAM 救援 → 縮舊 root → 新 LV 裝新系統 → 驗證後才切 ✅ 舊系統全程完好，直到新系統 SSH 登入驗證通過才放手
C 盲寫 autoinstall，整顆硬碟重來 ❌ 看不到畫面，一次失敗就要跑現場

選 B 的關鍵不是「技術上最漂亮」，而是它允許你在任何一步放棄。每一步結束時，機器都還是一台能 SSH 的完整系統。

🗺

整體設計：四個階段

階段在哪裡做做什麼風險
0 舊系統 → RAM 救援 kexec -e 進救援、SSH 驗證、reboot -f 回舊系統 零（不碰磁碟），目的只是證明退路真的通
1 RAM 救援內 e2fsck + 離線把 root 從 928G 縮到 60G，空出 VG 空間 中（縮檔案系統，但可先備份 LVM metadata）
2 舊系統內 debootstrap 把乾淨系統裝進新 LV（約 800G） 低（只是往新空間寫）
3 舊系統 → GRUB 加一次性開機項 + panic=10，用 grub-reboot 試開新系統 中，但有自動退回機制
4 新系統內 確認 OK → 設為預設 → 刪舊 LV、空間併回 低
📌 為什麼「縮檔案系統」一定要在 RAM 救援裡做？
因為 / 正在使用中，線上縮 ext4 是不允許的。而救援環境跑在記憶體裡、完全不依賴硬碟，所以它可以在「硬碟上的檔案系統是卸載狀態」時做這一刀。

反過來說，debootstrap 不能在救援裡做——救援只有 busybox 和 dropbear，沒有 apt、沒有套件庫工具鏈。這一步要等回到舊系統、有完整工具時再做。
🧱

難關一：做一個「一定會起來」的 RAM 救援

救援的內容物很精簡，但每一樣都是必需的：

元件用途
busybox（static）Shell 與所有基本指令（ip、insmod、reboot…）
dropbear + 動態庫SSH server，這就是你唯一的入口
網卡 kernel module沒有它就沒網路，等於沒救援
passwd / shadow / group讓密碼登入可用（這台機器沒有金鑰）
20 分鐘看門狗沒人連進來就自動 reboot -f 回舊系統

救援的 init 骨架大概長這樣（已簡化）：

#!/bin/busybox sh
# 1. 掛載必要檔案系統
mount -t proc proc /proc
mount -t devtmpfs dev /dev
mount -t devpts devpts /dev/pts # ← 少這行 SSH 一定連不上

# 2. 保險：20 分鐘後沒人就自己退回舊系統
( sleep 1200; reboot -f ) &

# 3. 載網卡模組、自動找介面、上 IP
while read -r mo; do insmod "$mo"; done < /etc/modules.list
for IF in enp2s0 eth0 eth1; do
  ip link set "$IF" up && ip addr add 203.0.113.88/28 dev "$IF" && break
done

# 4. 起 SSH
/usr/sbin/dropbear -R -g -p 22 -E &
✅ 看門狗是整個設計的核心。它讓「救援起來但連不上」從「災難」降級成「等 20 分鐘」。沒有 console 的機器上，這個 sleep 1200 && reboot -f 比任何漂亮的功能都重要。
🕳

難關二：四個「會讓你永久失聯」的細節

這四項都是在不碰磁碟的階段就該抓出來，否則等到真的切換系統才發現，就已經來不及了。

1. 沒有 /dev/pts：SSH 連上就斷

initramfs 只掛 devtmpfs 是常識，但很少有人想到 PTY。SSH 客戶端要求配置終端機時，dropbear 找不到 /dev/pts，登入直接被拒。

這個錯誤的長相是「連線成功 → 馬上斷線」，你幾乎無法從外部判斷原因。

2. 網卡模組是壓縮的 .ko.zst

Ubuntu 預設把 kernel module 壓成 .ko.zst。在 initramfs 裡用 busybox 的 insmod 去載入，很可能直接失敗——結果就是沒有網卡、沒有 IP、沒有 SSH。

# 打包時先解壓，讓 modules.list 指向未壓縮的 .ko
zstd -d -q -f -o "$ROOTFS$out" "$m"

3. 複製動態庫只帶到 symlink

cp -a 遇到 libfoo.so.1 -> libfoo.so.1.2.3 時複製的是連結，目標檔沒進 initramfs。結果 dropbear 一執行就 error while loading shared libraries。

正確做法：用 cp -L 解參照，同時放進 lib/x86_64-linux-gnu 與 usr/lib/x86_64-linux-gnu，補上 loader，再跑 ldconfig -r。

❌ 自己看檔案在不在

ls 看到檔案存在就以為沒問題——但 loader 路徑、ld.so.cache 都可能不對。

✅ 直接 chroot 實跑

chroot /tmp/rcheck /usr/sbin/dropbear -h：能印出 usage 才算真的能跑。

4. 網卡名稱在 initramfs 裡不是 enp2s0

沒有 udev 的環境下，介面通常叫 eth0。init 裡如果寫死 enp2s0，就會出現「模組載入了、但 IP 上不去」的狀況。

解法很土但有效：依序試 enp2s0 → eth0 → eth1，哪個成功上 IP 就 break。

⚠️ 還有一個容易漏的：如果你在 root shell 裡執行建置腳本，${SUDO_USER} 是空的，抓「使用者」會抓到 root——而 root 帳號通常是沒有密碼的，密碼登入永遠失敗。要嘛明確指定使用者，要嘛確認自己在正確的 shell 裡。
🎯

難關三：kexec_loaded=1 不代表你載對東西

這是整篇最值得記下來的一個坑。

kexec -l 只是把 kernel「預載」進記憶體，不會重開，所以它是一個很安全的測試。指令通常是：

kexec -l /boot/vmlinuz-$(uname -r) --initrd=/root/rescue/rescue.cpio.gz \
  --command-line='rdinit=/init panic=10 console=tty0'

我把它貼進終端時，反斜線續行被拆成了兩次執行：

$ sudo kexec -l /boot/vmlinuz-7.0.0-15-generic \
# ↑ 這一行就送出了：載入 kernel，但沒有 --initrd
$ --initrd=/root/rescue/rescue.cpio.gz \
-bash: --initrd=/root/rescue/rescue.cpio.gz: No such file or directory
$ echo $(cat /sys/kernel/kexec_loaded)
1

結果是：RAM 裡的 kernel 沒有 initramfs，但 kexec_loaded 照樣回報 1。

🛑 這個假陽性非常危險。如果這時候執行 kexec -e，機器會開進一顆沒有 /init 的 kernel → 直接 panic 或 hang。而救援 initramfs 裡的 20 分鐘看門狗根本還沒機會啟動（它就在那份沒被載入的 initramfs 裡），機器可能就這樣卡住，只能跑現場。

修正的做法：

  • 長指令一律單行，不要用 \ 續行
  • 載入前先 kexec -u 清空舊 image
  • 用 && echo LOAD_OK || echo LOAD_FAIL 明確判斷成敗
  • 真正的鐵證要等開機後看：
檢查救援環境（對）舊系統（錯）
/proc/1/commbusyboxsystemd
/proc/cmdline含 rdinit=/init含 root=/dev/mapper/...
ls /只有 bin sbin etc proc sys dev …有 boot、var、opt

附帶一個小技巧：很長、含多行 heredoc 的腳本不要直接貼。終端很容易吃掉某幾行，症狀是「腳本執行完全沒輸出」。改用 base64 分段寫入再解碼，並用 sha256sum 對雜湊驗證，一次就中。

🪂

難關四：讓「新系統開不起來」也能自己回來

Phase 3 要第一次開進新系統。沒有 console 的情況下，必須假設它可能會失敗，並且讓失敗自動復原。

機制作用
一次性開機項
grub-reboot		 只影響下一次開機，之後自動回到預設（舊系統）。不會忘記改回來。
panic=10 新系統掛不到 root 時會 panic，10 秒後自動重開 → 這次就走預設的舊系統
新系統自帶 /boot 安裝時不 bind 舊的 /boot，避免同版本 kernel 覆蓋舊系統的 vmlinuz-*
救援看門狗 Phase 0/1 期間如果連不上，20 分鐘後自動退回舊系統
📝 這裡有個容易忽略的細節：/boot 是獨立分割區時，新舊系統會共用同一個目錄。而 Ubuntu 的 kernel 檔名是 vmlinuz-<版本>——如果新系統裝了同版本 kernel，直接把舊系統的檔案蓋掉，舊系統就再也救不回來了。所以新系統的 /boot 要留在自己的 LV 裡。
📊

目前進度（誠實版）

寫這篇時只完成了 Phase 0 的準備：救援建置完成、在 chroot 裡實跑 dropbear 通過、kexec -l 回報 LOAD_OK。真正的切換演練還沒做，磁碟一個位元組都還沒動。

之所以先寫下來，是因為這些坑全部發生在不碰磁碟的階段——如果等到切換系統才踩到，代價就是跑一趟現場。把「不需要冒險就能發現的問題」全部提前發現，是整個流程裡最划算的部分。

🎓

教訓

  1. 先做「零風險的失敗」——Phase 0 不碰磁碟，專門用來證明退路真的通。先演練一次「進去、再回來」，比重灌本身更重要
  2. 狀態顯示成功 ≠ 做對事——kexec_loaded=1 只代表「有東西被載入」，不代表載入了 initramfs。驗證要看結果，不要看旗標
  3. 沒有 console 的機器，系統要能自己復原——看門狗、panic=10、一次性開機項，這三樣加起來才敢按下不可逆的那一步
  4. 在「不痛」的階段把坑踩完——/dev/pts、.ko.zst、symlink 動態庫、介面改名，全部都能在動磁碟前驗證
  5. 驗證要跑在真正會用到的那條路徑上——檔案在不在不等於能跑；chroot 實跑一次 dropbear -h 才算證據
