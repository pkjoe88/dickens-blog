沒有 IPMI、沒有序列埠（下）：四層自動退路，與一場沒人看的真機演練

D
Dickens
📅 2026-11-20 📖 13 分鐘閱讀 👁 1 次瀏覽

接續上篇：上篇寫到「Phase 0 準備完成，磁碟一個位元組都還沒動」。這篇是真正動刀的部分——離線縮 LVM、debootstrap 裝新系統、第一次開進新系統，然後最花時間的一步：讓它在開不起來的時候，自己退回舊系統。

💡 上篇的結論是「沒有 console 的機器，系統要能自己復原」。這篇把它變成具體的四層機制，而且每一層都用真實重開演練過——不是推論、不是文件上寫應該可以。事後看，真正救命的是「演練」這個動作本身，因為四層裡有三層第一次跑都有問題。
1

先把舊系統縮小：把空間讓出來

新系統要 200G，而整顆 root LV 是 928G、實際只用了 30G。作法是在救援環境（RAM 裡）把檔案系統縮小再切 LV——順序絕對不能顛倒，先縮 filesystem 再縮 LV，反過來就是資料毀損。

步驟指令為什麼
備份 LVM metadatavgcfgbackupLVM 自己也有設定，動刀前留一份
強制檢查e2fsck -f不乾淨的檔案系統不能 resize
縮檔案系統resize2fs /dev/… 60G離線縮，救援環境裡沒有掛載問題
縮 LVlvreduce -L 60G檔案系統已經先變小了，這裡才安全
再檢查一次e2fsck -f確認沒有把索引搞壞
# 救援環境（RAM 裡，uid 0） resize2fs /dev/ubuntu-vg/ubuntu-lv 60G The filesystem is already 15728640 (4k) blocks long. Nothing to do! lvreduce -L 60G /dev/ubuntu-vg/ubuntu-lv Size of logical volume ubuntu-vg/ubuntu-lv changed from 928.46 GiB to 60.00 GiB. Logical volume ubuntu-vg/ubuntu-lv successfully resized. vgs VG VSize VFree ubuntu-vg 928.46g 868.46g
📝 這裡踩到一個「檔案變大 12 倍」的坑：自己重打包 initramfs 時，如果 /proc、/sys 還掛在打包目錄底下，會被一起收進 image——83MB 瞬間變 968MB。打包前先 mount | grep "$WORKDIR" 確認是空的，這是零成本的檢查。

還有一個只有自己包的救援才會遇到的事：裡面沒有 vgs、lvs、lsblk、sha256sum。不是壞掉，是 busybox 沒有那些 applet——要改用 lvm vgs、wc -c 這類等價作法。

2

debootstrap：從零裝一個系統

回到舊系統（不用救援了），切出 200G 的新 LV，用 debootstrap 把最小系統放進去，再 chroot 進去補套件。

第一個坑是版本代號。這台是 Ubuntu 26.04 LTS，代號 resolute；我原本順手要寫 noble（那是 24.04），debootstrap 會直接找不到檔案。這種錯誤很便宜——在動任何分割區之前就會炸。

項目值備註
發行版Ubuntu 26.04 LTS代號 resolute
新 LVnewroot 200GUUID b43d0383…
基底安裝506 MB / 21,417 個檔案debootstrap 完成後的樣子
補完套件286 個Kernel、LVM、OpenSSH、sudo、netplan…
完成後用量3.0G對比舊系統的 30G

新系統的 /boot 刻意留在自己的 LV 裡面，chroot 時也不要把舊系統的 /boot bind 進去。原因上篇提過：/boot 是獨立分割區時，新舊系統共用同一個目錄，同版號 kernel 會直接覆蓋舊系統的檔案——那等於親手鋸掉自己的退路。

🔥 「連線斷了」不等於「指令停了」：遠端 apt-get install 跑到一半，我這邊的 SSH 客戶端等超過 180 秒、連線被切斷。第一反應是「壞了，要重跑」——但登入一看，apt-get 還在跑（etime 03:07），/var/cache/apt/archives 還在長大。

SSH 斷線只是少了觀察窗口，不是行程被殺。正確做法是「等它收工」而不是「重跑一次」，重跑只會撞 dpkg 鎖。後來腳本改成用迴圈等 apt-get 消失，再把客戶端等待時間拉到 25 分鐘。
📝 usermod -aG 只要有一個群組不存在，整條就失敗，而且一個群組都不會加。症狀是「帳號可以登入、但 sudo 完全不能用」。Ubuntu 的 lpadmin 群組是印表機套件帶的，最小安裝沒有。先 getent group 檢查並補建，加完再用 id 驗證——不要只看指令有沒有噴錯。

還有一個「以為壞了、其實正常」的：systemctl is-enabled ssh.service 顯示 disabled，但 ssh.socket 是 enabled。新版 OpenSSH 走 socket activation，這樣才是對的。如果只查 ssh.service 就補強制 enable，反而多一個不必要的手動設定。

最後一個關鍵驗證：root 在 LV 上，所以 initramfs 必須能啟用 LVM。不能只看「有裝 lvm2」，要直接問 initramfs：

lsinitramfs /boot/initrd.img-7.0.0-15-generic | grep -cE '(^|/)lvm$' 2 # 0 的話這台機器一定開不起來——initramfs 找不到 root
3

第一次開進新系統：31 秒

做法是「一次性開機項」：在 GRUB 寫一個指向新 LV 的 menuentry，用 grub-reboot 只讓下一次開機選它，之後自動回到預設。

這裡有個決策值得記下來：第一次試開，用「已經在舊系統上跑了好幾個月」的核心，而不是 repo 裡最新的那顆。新系統裝了 7.0.0-43（最新）和 7.0.0-15（舊系統正在用的），第一次開機刻意選 15——把「新系統」和「新核心」這兩個變數拆開，一次只驗一個。

🔥 我以為我重開了，其實沒有。 systemctl reboot 用非 root 身分執行回傳 rc=1（權限不足），機器完全沒動。但我的腳本只印了「reboot issued」，然後繼續等 SSH——等到的當然是舊系統，於是「驗證」得出「新系統開不起來」的錯誤結論。

救回來的關鍵是 uptime：它顯示 2766 秒。重開過的機器不可能有 2766 秒的 uptime。任何「我已經重開了」的判斷，都要用 uptime 或開機時間驗證，不要相信指令的 exit code。

真的重開之後，31 秒連回新系統：

檢查結果
根裝置/dev/mapper/ubuntu--vg-newroot（不是舊的）
核心命令列root=UUID=b43d0383… ro panic=10
failed units0（舊系統反而有一個 openipmi 失敗，因為機器沒有 IPMI 硬體）
網路enp2s0 固定 IP、State: routable (online)、driver igc
磁碟196G，用 3.0G
登入用原本的帳號密碼走真 SSH 連上（不是 chroot 測試）
4

四層退路：讓它學會自己認輸

新系統能開，但真正的問題現在才開始：我人在遠端，它如果哪天開不起來，誰來救？沒有 console，選單上的東西我永遠看不到。

所以「預設開新系統」這件事必須搭配自動退路。最後做成四層，各有各的觸發條件：

層觸發條件動作
1. 核心存在性守衛 新系統上的 vmlinuz-7.0.0-15 不見（例如被 apt autoremove） 改開 7.0.0-43；再不見就退回舊系統
2. 重試鏈 連續 2 次開機都沒能「證明自己活著」（例如核心 panic 一直重開） 第 3 次直接開舊系統
3. 網路看門狗 開起來了，但 8 分鐘內 ping 不到 gateway 或 22 埠沒開 把 GRUB 的 next_entry 指向舊系統 → reboot -f
4. 關機清計數器 正常關機（不是 reboot -f） 清掉重試計數器，避免「短時間連續重開兩次」被誤判成開機失敗

第 2 層的「計數器」是這套設計的核心，它把「開機成功」定義成一件可以被證明的事：開機 45 秒後，ping 得到 gateway 而且 22 埠有在聽，才把 sau_try1、sau_try2 清掉。只要沒清，下一次開機 GRUB 就往上計數；滿兩次，第三次直接換人。

# grubenv 的計數器長這樣（由 GRUB 自己在開機時寫入） next_entry= sau_try1=1 # ↑ 這次開機還沒被證明成功；45 秒後 boot-ok 成功才會清掉

刻意保留的不對稱：reboot -f（看門狗用的）不清計數器，正常關機才清。前者代表「系統覺得自己不對勁」，後者代表「人為、有秩序地重開」。

⚠

三個最貴的坑

🔥 坑一：set -u 加上沒加引號的 heredoc，把 GRUB 設定寫成 0 bytes。

腳本裡用 heredoc 產生 40_custom，裡面有一個沒定義的變數。在 set -u 下展開失敗，檔案被寫成 0 bytes，而 update-grub 照樣回報成功（它只是「讀一個空檔」）。接著 grub-reboot '某個標題' 也照樣寫進了 next_entry——指向一個根本不存在的選單項目。

如果這時候機器剛好重開，GRUB 找不到那個項目，就是「無 console 機器徹底失聯」。修法有兩個：heredoc 一律用 <<'EOF' 不做展開；以及寫 next_entry 之前一定要 grep 確認那個 menuentry 真的在 grub.cfg 裡。
🔥 坑二：備份檔放在 /etc/grub.d/ 裡，被當成設定執行。

改 40_custom 前先備份成 40_custom.p4bak-…，想說「同目錄很方便」。結果 grub-mkconfig 會執行該目錄下所有符合命名規則的檔案，備份被當成第二份設定，grub.cfg 就出現兩個同名項目。備份要放到目錄外。
🔥 坑三：chroot 裡跑 update-grub，忘了把 /boot 分割區掛進去。

舊系統的 /boot 是獨立分割區。chroot 進去看到的是空目錄，grub.cfg.new 寫不進去、指令回 rc≠0。正確做法是 mount /dev/nvme0n1p2 /mnt/old/boot——掛在目標系統的 /boot，不是另外一個掛載點。

還有兩個比較小的：grep 'set default=' 第一個命中其實是 GRUB 標頭裡處理 next_entry 的那行（驗證條件寫錯，會誤判成「沒改成功」）；以及兩個行程同時掛載／卸載同一個掛載點時，grub-editenv 會噴 cannot open grubenv.new——後來乾脆讓腳本永遠不卸載，只做「沒掛就掛」。

🧪

然後是演練：八次真實重開

機制寫完不等於有效。對一台沒有 console 的機器，「應該可以」跟「已經驗證」之間的差距，就是跑一趟現場。所以每一層都排了演練：

#動作預期結果
A正常重開新系統，45 秒後計數器自動清✅ 30 秒連上
B手動填滿 sau_try1/2 再重開舊系統✅ 重試鏈生效
C清空計數器再重開回新系統✅
Dnext_entry=舊系統 再重開舊系統，且 GRUB 自動消費掉 next_entry✅
E不設 next_entry 重開新系統✅
F把守衛檢查的檔名改成不存在的版本自動改開 43✅ 順帶證明 43 也能開機
G植入 sau_try1=1 後正常重開仍進新系統（關機清理有效）✅ sau_try2 沒被寫
H開機 100 秒總檢grubenv 只剩 next_entry=、兩個 timer 都 active✅ failed units 0
✅ 演練 F 是意外收穫：本來只是要驗證「核心不見時會不會換項目」，結果同時證明了 7.0.0-43 這顆從未開機過的核心也能正常開機。等於多了一條可用的備援路線。

還有一個「不演練就會變成不定時炸彈」的地方：看門狗本身。網路正常時它應該什麼都不做——所以要手動觸發它，確認它真的不會誤重開（Result=success、uptime 持續增加）。沒測過的救援機制，跟沒有一樣。

📡

觀察期：讓排程代替人盯著

新系統上線後不該馬上刪舊系統，留 14 天觀察。但「記得每天檢查」是人最容易出錯的地方，所以做成排程：每天 09:30 用 SSH 做一次唯讀檢查，把結果推 LINE。

SAU0 每日檢查　觀察期 3/14 系統：新系統 NEW（newroot） 核心：7.0.0-15-generic 開機：2 天 3 小時 服務：failed 0｜SSH OK 磁碟：196G 已用 3.0G（2%） GRUB：next_entry=

幾個小設計：連不上也要回報（含連續失敗次數），否則最糟的情況是「它死了，而你以為它沒事」；推送失敗不推進「今天已報」的狀態，隔天才會重試；只做唯讀檢查，不做任何變更。

刻意不把「刪除舊系統」也做成排程。搬 /boot、grub-install、lvremove 這幾步在無 console 的機器上不可逆，一次無人操作失敗就再也進不去。期滿只發通知，實際動手留給一次有人盯著的 session。

🎓

這次的教訓

  1. 「指令回 0」不代表「事情做了」——update-grub 讀到空檔也回成功；systemctl reboot 權限不足只會回 rc=1，機器動都不動。要看結果，不要看 exit code
  2. 連線中斷 ≠ 行程被殺——SSH 斷了，遠端的 apt-get 還活著。先確認，再決定要不要重跑
  3. 退路要能「被證明」——把「開機成功」定義成「ping 得到 gateway 且 22 埠有聽」，計數器才有意義；用「我覺得它應該起來了」當成功條件，退路永遠不會啟動
  4. 一次只驗一個變數——新系統配舊核心。兩個都新的話，失敗了不知道該懷疑誰
  5. 沒有 console 的機器，最貴的坑都在「設定檔被寫壞」而不是「服務起不來」——服務掛了還能 SSH 進去看；grub.cfg 壞了，你連開機都到不了。所以新邏輯放在不會被覆蓋的 custom.cfg，每次改完都跑 grub-script-check
  6. 演練本身就是開發——四層裡有三層第一次跑有問題（競態、計數器時序、驗證條件），全部是演練時才現形
📝 目前狀態：新系統是預設、舊系統 60G 完整保留、每天 LINE 回報。等觀察期滿，才會做最後一步（新系統接手 GRUB、回收舊 LV）。在那之前，任何一次重開都會自動回到新系統；真的出事，四層退路會把它送回舊系統。
